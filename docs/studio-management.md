# Услуги и мастера из админки — VESPERA

Каталог студии редактируется через админку и лежит в `data/studio.json`
(на Vercel — строка `studio` в Postgres). `src/lib/studio.ts` остался источником
типов и seed-значений: если документа нет, сайт работает на них.

Удаление — **физическое**. История броней держится на снапшотах названий.
Архива и восстановления больше нет.

- Базовый префикс: `/api/admin/studio`
- Авторизация: cookie `vespera_admin`, каждый роут проверяет `requireAdmin`
  (управлять каталогом может и `owner`, и `manager`)
- Часы работы и шаг сетки (12:00–22:00, 30 минут) не редактируются — это `STUDIO_HOURS`
- `cache-control: no-store`; после каждой мутации сервер зовёт `revalidatePath("/")` и `/admin`

## Модель данных

`data/studio.json` (создаётся при первой мутации, в git не попадает):

```json
{
  "version": 1,
  "updatedAt": "2026-11-16T10:00:00.000Z",
  "services": [
    {
      "id": "svc-k3m9x2qp",
      "slug": "piling-test",
      "name": "Пилинг-тест",
      "durationMin": 45,
      "priceRub": 3000,
      "description": "Тестовая",
      "ritual": "40 минут"
    }
  ],
  "masters": [
    {
      "id": "ms-eva",
      "slug": "eva-kim",
      "name": "Ева Ким",
      "role": "макияж, свет",
      "years": 7,
      "serviceIds": ["svc-makeup", "svc-nails"],
      "workingDays": [0, 3, 4, 5, 6]
    }
  ]
}
```

Правила:

1. **`id` неизменяем и случаен:** `svc-xxxxxxxx` / `ms-xxxxxxxx` (8 символов).
   Генерируется один раз и не зависит от `slug` — поэтому удалённая и заново созданная
   услуга с тем же slug получает **новый** id, и старые брони не «приклеиваются» к ней.
   Старые id из прежних документов (`svc-skin`, `ms-eva`) продолжают работать как есть.
2. `slug` человекочитаемый и уникальный (kebab-case). Можно менять: брони ссылаются на `id`.
3. `workingDays` — `0` (воскресенье) … `6` (суббота), без повторов, минимум один день.
4. `serviceIds` мастера — только существующие услуги. При удалении услуги её id
   вычищается из всех мастеров.
5. `version` и `updatedAt` служебные (`updatedAt` — момент последней записи).
6. Перед перезаписью прежняя валидная версия уходит в `data/studio.json.bak`.

## История броней: снапшоты

Имя услуги и мастера не должно зависеть от того, что сейчас лежит в каталоге.
Поэтому в каждой брони хранятся четыре дополнительных поля:

```json
{
  "serviceId": "svc-k3m9x2qp",
  "serviceName": "Пилинг-тест",
  "serviceSlug": "piling-test",
  "masterId": "ms-eva",
  "masterName": "Ева Ким",
  "masterSlug": "eva-kim"
}
```

- **При создании** брони (публичной и ручной) снапшот пишется сразу из каталога.
- **При удалении** услуги или мастера сервер сначала проходит документ `bookings`
  и проставляет недостающие `serviceName`/`masterName` (и slug) во все брони,
  которые ссылаются на удаляемую запись, и только потом удаляет её из каталога.
  Заполняются только пустые поля: снимок, сделанный при записи, не перезаписывается.
- **При чтении** брони имя берётся из каталога, а если записи там уже нет — из снапшота.
  Поэтому `GET /api/booking/{code}`, админский список, карточка брони и экран успеха
  показывают название и после удаления.
- Календарь и сводки услуги по именам не резолвят вовсе — они считают по `durationMin`
  и `priceRub`, которые в брони тоже снимком. Отсутствие записи в каталоге их не ломает.

Если бронь ссылается на удалённую услугу, `service.slug` в ответе может быть пустым,
а `service.id` остаётся исходным (он же `serviceId` брони). `service.name` — из снапшота.

## Чтение, кэш и устойчивость

- Данные лежат в слое хранения: локально — `data/studio.json`, на Vercel — строка `studio`
  в Postgres. Подробности и переключение: `docs/storage.md`.
- Каталог кэшируется в памяти **не дольше секунды** и сбрасывается после каждой записи:
  слоты не ходят в хранилище за каждым слотом, а правка видна сразу.
- Битый JSON → читаем `.bak`; битые оба → seed-дефолты из `studio.ts`. Сайт работает всегда.
- Запись атомарна: локально — очередь в процессе и `rename`, в Postgres — транзакция
  с advisory lock на документ. Две одновременные правки не теряются.
- `VESPERA_DATA_DIR` уводит файловое хранилище в другой каталог (удобно для e2e).

## Эндпоинты

Все ответы — `{ ok: true, ... }` или `{ ok: false, error, message, details? }`.
Без cookie — `401 { "error": "unauthorized" }`.

### GET /api/admin/studio

```bash
curl http://localhost:3000/api/admin/studio -b cookies.txt
```

```json
{
  "ok": true,
  "services": [ /* все, флага archived больше нет */ ],
  "masters": [ /* все */ ],
  "rituals": [ { "id": "ritual-quiet-hour", "name": "Тихий час", "description": "…", "serviceIds": ["svc-skin"] } ],
  "updatedAt": "2026-11-16T10:00:00.000Z"
}
```

Ритуалы пока не редактируются — отдаются из seed.

### POST /api/admin/studio/services — создать услугу

| Поле | Обяз. | Правила |
| --- | --- | --- |
| `name` | да | 2–60 символов |
| `slug` | нет | kebab-case, 2–48, уникальный; иначе генерируется из `name` (транслит) |
| `durationMin` | да | целое, 15–240, кратно 15 |
| `priceRub` | да | целое, 0–200 000 |
| `description` | нет | ≤ 300 |
| `ritual` | нет | ≤ 80 |

```bash
curl -X POST http://localhost:3000/api/admin/studio/services \
  -H "Content-Type: application/json" -b cookies.txt \
  -d '{"name":"Пилинг-тест","durationMin":45,"priceRub":3000,"description":"Тестовая","ritual":"40 минут"}'
```

`201`:

```json
{
  "ok": true,
  "service": {
    "id": "svc-k3m9x2qp",
    "slug": "piling-test",
    "name": "Пилинг-тест",
    "durationMin": 45,
    "priceRub": 3000,
    "description": "Тестовая",
    "ritual": "40 минут"
  }
}
```

`409 slug_taken` — если `slug` задан явно и уже занят:

```json
{ "ok": false, "error": "slug_taken", "message": "slug «skin-ritual» уже занят", "details": { "slug": "skin-ritual" } }
```

`400` — валидация: `{ "error": "invalid_request", "message": "Длительность кратна 15 минутам" }`.

### PATCH /api/admin/studio/services/{id}

`{id}` — `id` или `slug`. Поля те же и все необязательные; пустое тело → `400 «Нет полей для изменения»`.

```bash
curl -X PATCH http://localhost:3000/api/admin/studio/services/svc-k3m9x2qp \
  -H "Content-Type: application/json" -b cookies.txt \
  -d '{"priceRub":7000,"durationMin":60}'
```

`200 { ok: true, service: {...} }`; `404` — нет такой услуги; `409 slug_taken`.

Правка `priceRub`/`durationMin` **не** трогает старые брони (в них снимок), но свободные
слоты считаются по новой длительности сразу.

### DELETE /api/admin/studio/services/{id} — удалить услугу

Убирает запись из каталога физически и вычищает её `id` у всех мастеров.
Перед удалением названия дописываются в старые брони.

**200:**

```json
{ "ok": true, "service": { "id": "svc-k3m9x2qp", "slug": "piling-test", "name": "Пилинг-тест" }, "bookingsUpdated": 3 }
```

`bookingsUpdated` — сколько броней получили снапшот (0, если их не было).

**409 delete_conflict** — есть **будущие активные** брони (`confirmed`, дата/время ≥ сейчас).
Прошлые, отменённые, завершённые и неявки удалению не мешают:

```json
{
  "ok": false,
  "error": "delete_conflict",
  "message": "Нельзя удалить услугу: есть будущие записи (VSP-4NCP). Отмените или перенесите их",
  "details": {
    "bookings": [{ "code": "VSP-4NCP", "date": "2026-11-18", "time": "18:00", "name": "Гость теста" }]
  }
}
```

**409 masters_without_services** — после удаления у мастера не осталось бы ни одной услуги.
Сначала назначьте ему другую услугу:

```json
{
  "ok": false,
  "error": "masters_without_services",
  "message": "Удаление оставит мастеров без услуг (Ева Ким). Сначала назначьте им другие услуги",
  "details": { "masters": [{ "id": "ms-eva", "name": "Ева Ким" }] }
}
```

`404` — нет такой услуги.

### Мастера

| Эндпоинт | Что делает |
| --- | --- |
| `POST /api/admin/studio/masters` | создание |
| `PATCH /api/admin/studio/masters/{id}` | правка |
| `DELETE /api/admin/studio/masters/{id}` | удаление (те же `409 delete_conflict` по будущим броням мастера, `404`) |

Эндпоинтов `/restore` больше нет: восстановить удалённую запись нельзя, создайте заново.

Поля: `name` 2–60, `slug` (kebab-case, уникальный, иначе из имени), `role` ≤ 80,
`years` 0–60, `serviceIds` — минимум одна **существующая** услуга,
`workingDays` — непустой массив уникальных чисел 0–6.

```bash
curl -X POST http://localhost:3000/api/admin/studio/masters \
  -H "Content-Type: application/json" -b cookies.txt \
  -d '{"name":"Тест Мастер","role":"тест","years":3,"serviceIds":["svc-skin"],"workingDays":[1,2]}'
```

```json
{
  "ok": true,
  "master": {
    "id": "ms-7fq2k9dm",
    "slug": "test-master",
    "name": "Тест Мастер",
    "role": "тест",
    "years": 3,
    "serviceIds": ["svc-skin"],
    "workingDays": [1, 2]
  }
}
```

`400` при ссылке на несуществующую услугу:

```json
{
  "ok": false,
  "error": "invalid_request",
  "message": "Проверьте serviceIds мастера — Нет таких услуг: svc-nope",
  "details": { "fields": [{ "field": "serviceIds", "message": "Нет таких услуг: svc-nope" }], "invalidIds": ["svc-nope"] }
}
```

`DELETE /api/admin/studio/masters/{id}` возвращает `{ ok: true, master, bookingsUpdated }`
и так же дописывает имена в брони перед удалением.

## Что происходит с записью и календарём

| Место | Изменение |
| --- | --- |
| `GET /api/booking/availability` | удалённой услуги/мастера нет → `reason: "unknown_service"` / `"unknown_master"`; новые `workingDays` и `durationMin` применяются сразу |
| `POST /api/booking` | удалённые не принимаются (`400`), цена и длительность — серверные, снапшот имени пишется в бронь |
| `GET /api/admin/calendar` | считает по броням; удалённые услуги/мастера в справочнике не нужны — сводки не падают |
| `GET /api/admin/bookings` | фильтр по удалённому мастеру работать перестаёт (его нет в списке `masters`), но его старые брони остаются в списке с именем из снапшота |
| Карточка брони | имя удалённой услуги/мастера берётся из снапшота |

Существующие брони после правки каталога не пересчитываются и не переносятся:
в них снимок `durationMin`/`priceRub` на момент записи. Меняется только то,
какие слоты предлагаются дальше.

## Как сбросить каталог к дефолтам

```bash
rm -f data/studio.json data/studio.json.bak
```

```powershell
Remove-Item data/studio.json, data/studio.json.bak -ErrorAction SilentlyContinue
```

Перезапуск не нужен: файла нет → отдаются seed-дефолты из `src/lib/studio.ts`
(кэш живёт не дольше секунды). Брони не трогаются — они ссылаются на `id`,
которые в дефолтах те же.

Если каталог уже переехал в Postgres:

```sql
DELETE FROM vespera_documents WHERE name = 'studio';
```

## Ограничения

- Ритуалы (`RITUALS`) пока не редактируются, отдаются из seed.
- Часы работы, шаг сетки и лид-тайм не редактируются — это `STUDIO_HOURS`.
- Удаление необратимо: восстановления и «корзины» нет.
- Удаление услуги, которая ещё закреплена за мастером, разрешено только если у мастера
  останутся другие услуги — иначе `409 masters_without_services`.
- Проверка будущих броней и удаление — два шага, окно гонки в миллисекунды: бронь,
  созданная ровно между ними, останется ссылаться на удалённую услугу. История от этого
  не страдает (снапшот пишется при создании), но запись придётся отменить вручную.
- Снапшоты заполняются только у пустых полей: если услугу переименовали после записи,
  в брони останется имя на момент записи — это и есть смысл снимка.
