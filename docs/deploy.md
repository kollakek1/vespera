# Деплой VESPERA на Vercel

**Текущий прод:** https://vespera-lovat.vercel.app
(проект `vespera`, регион функций `iad1`, база Neon `us-east-1`)

Проверено на прод-конфигурации (та же база, `next start` с `DATABASE_URL`):
создание брони → `201`, чтение по коду, вход владельцем → `200`, список броней и календарь отдают запись,
после перезапуска процесса бронь на месте — значит данные в Postgres, а не в памяти.

Репозиторий публикуется на GitHub, но деплой от него не зависит: Vercel собирает проект
из локальной папки. На этой машине прямой `vercel --prod` падает с `fetch failed`,
поэтому используется обходной путь: preview-деплой → `vercel promote`.

## 1. Что нужно до первого деплоя

| Переменная | Обязательна | Значение |
| --- | --- | --- |
| `DATABASE_URL` | да (на Vercel) | строка Neon, вида `postgresql://user:pass@host/db?sslmode=require` |
| `ADMIN_SESSION_SECRET` | да | 64 hex-символа, подпись cookie |
| `ADMIN_PASSWORD` | да при первом запуске | пароль владельца, ≥ 12 символов; дальше используется только для bootstrap |
| `ADMIN_EMAIL` | нет | email владельца, по умолчанию `admin@vespera.studio` |

Локально без `DATABASE_URL` приложение работает на файлах в `data/` — это нормально для разработки.
На Vercel файловая система read-only, поэтому база обязательна: иначе брони и каталог не сохранятся.

Секреты не коммитятся: `.env.local` покрыт `.gitignore`, в Vercel значения задаются как env проекта.

## 2. База

Вариант A — интеграция Neon через CLI:

```sh
cd vespera
vercel link
vercel integration add neon --yes
vercel env pull .env.vercel.local   # проверить, что DATABASE_URL появился
```

Вариант B — вручную: создать проект в Neon, скопировать connection string и добавить его в Vercel → Project → Settings → Environment Variables (`DATABASE_URL`, все окружения).

Схема создаётся идемпотентно при первом обращении: таблица `vespera_documents (name text primary key, data jsonb, updated_at timestamptz)`.
Документы: `bookings`, `studio`, `admins`.

## 3. Секреты в Vercel

```sh
vercel env add ADMIN_SESSION_SECRET production
vercel env add ADMIN_PASSWORD production
# ADMIN_EMAIL — опционально
```

Или через `vercel env pull` / дашборд. После изменения env нужен повторный деплой.

## 4. Деплой

```sh
cd vespera
vercel link                 # привязать папку к проекту
vercel --prod               # продакшн-сборка и выкладка
```

Проверить статус и логи:

```sh
vercel inspect <deployment-url>
vercel logs <deployment-url>
```

## 5. Проверка после выкладки

1. Открыть прод-URL: hero, 3D, скролл, мобильная вёрстка.
2. Пройти запись: услуга → мастер → дата/время → контакты → получить код.
3. `/admin`: войти владельцем, увидеть эту бронь в календаре дня.
4. Создать услугу в разделе «Студия», обновить лендинг — услуга появилась.
5. Дождаться холодного старта (или сделать второй запрос через паузу) и убедиться, что бронь и услуга на месте — значит база пишется, а не `/tmp`.
6. Проверить отказ: неверный пароль → 401, шестая попытка → 429.

## 6. Ограничения текущей версии

- Вся история броней хранится одним JSON-документом и перезаписывается целиком. Для одной студии нормально, для тысяч записей нужна нормализация в таблицы.
- Rate limit логина и заявок живёт в памяти инстанса: на нескольких лямбдах лимит действует на каждую отдельно.
- Смена пароля администратора не отзывает уже выданные сессии (деактивация отзывает за ≤ 5 секунд).
- Удаление документа `admins` возвращает доступ по `ADMIN_PASSWORD`, но теряет остальных администраторов.
- Если `DATABASE_URL` не задан на Vercel, приложение не упадёт, но записи будут теряться между запросами.

## 7. Откат

```sh
vercel rollback            # вернуться на предыдущий деплой
```

Данные в Neon при откате кода не меняются: схема документов совместима в обе стороны.
